How the two directions are implemented

Some online tools decode entities by assigning your text to a live element's innerHTML, which parses it as markup: a pasted <img onerror=…> executes on the spot. This tool never does that.

  • Escaping is pure string replacement: a character-to-entity table applied with a regular expression. No parser is involved, so nothing can be interpreted.
  • Unescaping uses a detached <textarea>: a textarea's content is RCDATA in the HTML specification, meaning the parser decodes character references but never creates elements from it. That gives full coverage of every named and numeric entity with no execution path, and the element is never attached to the page.
  • Bidirectional Sync: Paste raw code on the left to secure it for transport, or paste an escaped payload on the right to revert it to readable HTML instantly.
  • Air-Gapped Operation: No payload data is ever transmitted to external servers. All cryptographic string manipulation occurs locally.

The five characters, and the order they must be replaced in

HTML escaping replaces characters that carry structural meaning with entity references. There are five that matter, and one ordering rule that catches people out:

  • & → &amp; — must be replaced first, or you re-escape the semicolons of your own entities and produce &amp;lt;, which renders visibly as &lt;.
  • < → &lt; and > → &gt; — otherwise your value starts or ends a tag.
  • " → &quot; and ' → &#39; — these end a quoted attribute value. Prefer the numeric &#39; over &apos;, which was not in HTML 4 and is unrecognised by some legacy parsers.

Get that right and a value is safe in exactly one context: as text between tags. Everywhere else needs different handling, which is the subject of our guide on contextual output escaping.

Unquoted attributes

<input value={{ x }}> is unsafe even when escaped, because an unquoted value ends at the first space. A payload of x onfocus=alert(1) autofocus contains none of the five characters and adds an event handler. Always quote attributes.

Inside <script>

HTML escaping is the wrong tool here and corrupts the data. Worse, the literal text </script> ends the block even inside a JavaScript string, because the HTML tokeniser runs before the JS parser. Serialise as JSON into a data attribute instead.

Inside href

Escaping produces well-formed HTML and does not help: javascript:alert(1) contains no character that escaping touches. The defence is a scheme allowlist — accept http:, https:, mailto: and reject the rest.

Escape on output, never on input

A persistent anti-pattern is escaping values as they arrive and storing the escaped form. It fails for three reasons worth knowing:

  • The context is unknown at input time. The same comment might later be rendered as HTML, sent as a plain-text email, returned in a JSON API response and included in a CSV export. Each needs different treatment, and HTML entities in a plain-text email are simply wrong.
  • Your data is corrupted. The stored value is no longer what the user typed, so search, sorting, length checks and comparisons all operate on &amp; instead of &.
  • Double escaping. When a correctly written template escapes the already-escaped value, users see &amp;lt; on the page — and the usual "fix" is to disable escaping in that template, which removes the real protection.

Store exactly what the user typed; escape at the moment of rendering, for the destination it is rendering into. This tool's unescape direction is genuinely useful for diagnosing the double-escaping case: paste the mangled output and you can see how many rounds of escaping it went through.

Escaping is not sanitising

These solve different problems. Escaping renders a value as inert text, so <b>hi</b> displays as those literal characters — correct for usernames, titles and comments. Sanitising parses the value as HTML and strips everything not on an allowlist while keeping the rest live — correct only when users are meant to submit formatting. If you need sanitising, use a maintained library such as DOMPurify and never a regular expression: HTML is far too irregular for pattern matching, and every hand-rolled tag stripper has been bypassed via malformed markup that browsers helpfully "correct" into something executable.
