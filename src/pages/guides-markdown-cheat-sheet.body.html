Markdown Cheat Sheet: GitHub-Flavored Syntax With Examples

Markdown is the format of README files, documentation sites, issue trackers, chat apps and note-taking tools. The core syntax fits on a page, but the details that trip people up, such as line breaks, nested lists, tables and escaping, differ between the original specification, CommonMark and GitHub-Flavored Markdown. This sheet shows the syntax that renders the same everywhere, marks the extensions that do not, and explains the rules behind the surprises.

Layerbit Engineering Published 18 October 2026 8 min read

The short version

  • Separate paragraphs, lists, headings and code blocks with a blank line. Most "it didn't render" problems are a missing blank line.
  • A single line break inside a paragraph is ignored; end the line with a backslash or two spaces to force a break.
  • Fenced code blocks (three backticks plus a language name) are the reliable way to show code.
  • Tables, task lists, strikethrough and automatic links are GitHub-Flavored Markdown extensions, supported by most modern renderers.
  • Escape any special character with a backslash: \*, \_, \#, \|.

Markdown, CommonMark and GFM

John Gruber's original Markdown of 2004 was a short description plus a Perl script, and it left many cases ambiguous, so every implementation behaved slightly differently. CommonMark, first published in 2014, is a precise specification with hundreds of examples that resolves those ambiguities; most serious parsers now follow it. GitHub-Flavored Markdown (GFM) is CommonMark plus a small set of extensions: tables, task lists, strikethrough, extended autolinks and filtering of some raw HTML. When this sheet says something works "everywhere", it means CommonMark; GFM extensions are labelled.

That last note is a classic surprise. A line of text followed directly by --- becomes a level-2 heading (a "setext" heading), and one followed by === becomes level 1. Leave a blank line before a horizontal rule.

Paragraphs and line breaks

Markdown joins consecutive lines into one paragraph, so text wrapped at 80 columns in the source still flows as a paragraph. Start a new paragraph with a blank line. To force a line break without a new paragraph, for an address or a poem, end the line with a backslash, which is visible and survives editors that trim trailing whitespace, or with two spaces, which works everywhere but is invisible. Some environments, GitHub comments and issues among them, treat every newline as a break; README files on GitHub do not. Our Markdown editor has a "Line breaks" switch to preview either behaviour.

The rule behind nesting is that a child item must be indented at least as far as the text of its parent, not its marker. For - item that is two spaces; for 1. item it is three. Four spaces always works, which is why many style guides recommend it. A paragraph or code block inside a list item needs the same indentation, plus a blank line before it.

Heading anchors are generated by the renderer, not by Markdown itself. GitHub's rule, which most tools copy, lower-cases the text, removes punctuation and replaces spaces with hyphens, so ## Getting Started! becomes #getting-started; a repeated heading gets -1, -2 and so on. Always write useful alt text for images: it is what screen readers announce and what appears when the image fails to load.

Put the language name directly after the opening fence for syntax highlighting: js, ts, python, bash, json, yaml, sql, diff and many more are recognised by GitHub, GitLab and most documentation generators. To show a fence inside a code block, open the outer block with four backticks.

Tables (GFM)

| Endpoint      | Method | Auth   |
| :------------ | :----: | -----: |
| /orders       | GET    | token  |
| /orders/{id}  | DELETE | admin  |

The second line is required: it separates the header and sets alignment with colons, left (:---), centre (:---:) or right (---:). The pipes do not need to line up in the source. A literal pipe inside a cell must be escaped as \|, cells cannot contain block content such as lists or multiple paragraphs, and a line break inside a cell needs an HTML <br>. For anything more complex, an HTML table or a link to a spreadsheet is clearer.

Escaping and raw HTML

A backslash before any ASCII punctuation character makes it literal: \*not italic\*, \# not a heading, 1\. not a list. Inside inline code and code blocks nothing needs escaping. Most renderers also accept raw HTML, such as <details> for collapsible sections, <kbd> for keys and <sup> for superscripts. GitHub and most hosted platforms sanitize it, removing scripts, event handlers and styles. If you render user-written Markdown in your own application, sanitize the generated HTML with a library such as DOMPurify; escaping the input is not enough, because Markdown syntax itself produces HTML. Our guide to HTML escaping and XSS contexts explains why.

GitHub-only extras

Some popular features are specific to GitHub and will appear as plain text elsewhere: @username mentions and #123 issue references; footnotes written as [^1]; alerts written as > [!NOTE], > [!WARNING] and similar; emoji shortcodes such as :rocket:; and Mermaid diagrams in a ```mermaid fence. They are worth using in a repository, but avoid them in documentation that will also be rendered by another tool.
