What the formatter does, and does not do

Formatting XML is not just inserting newlines. Whitespace inside an element is data unless the schema says otherwise, so a naive pretty-printer that indents everything changes the meaning of <p>Hello <b>world</b></p>. This tool parses the document with the browser's DOMParser, then re-serialises the tree with a rule: an element whose children are all elements is broken across lines and indented; an element that contains text stays on one line with its text untouched. Comments, CDATA sections and processing instructions are preserved unless you strip them. Attribute order is preserved as written.

Reading a SOAP or SAML response

Enterprise APIs still return dense single-line XML. Paste the body here to see the structure, then use XPath to pull the one value you need — //soap:Fault/faultstring or //saml:Attribute[@Name='email']/saml:AttributeValue — without writing a parser for a one-off check.

Finding the well-formedness error

"XML parsing error" from a library rarely says where. The browser's parser reports the line and column of the first problem, and the tool shows it with the offending line. The usual culprits are an unescaped & in text, a mismatched closing tag, an attribute without quotes, or a BOM or stray character before the <?xml declaration.

XML to JSON for a quick look

The JSON mode gives a compact object view: attributes as keys prefixed with @, text as #text when an element has both, repeated child elements collapsed into arrays. It is meant for reading and for quick scripts, not as a lossless conversion — namespaces, comments and element order across siblings of different names are not representable in a plain object.

Config files and feeds

Maven pom.xml, web.config, Android manifests, RSS and Atom feeds, SVG, plist — all XML, all readable here. For SVG, formatting is safe; for feeds, an XPath like //item[1]/pubDate answers "when did this last update" faster than opening a reader.

Browsers implement XPath 1.0, so functions from XPath 2.0 and 3.1 — matches(), string-join(), for … return — are not available, and a query that uses them fails with a syntax error. The four result types are what XPath 1.0 has: a node set, a string, a number or a boolean, and the tool labels which one you got.

The namespace trap

The most common reason an XPath returns nothing is a default namespace. An Atom feed declares xmlns="http://www.w3.org/2005/Atom" on its root, which puts every element in that namespace; //entry then matches nothing, because in XPath 1.0 an unprefixed name means "no namespace", not "any namespace". You must bind a prefix and write //ns:entry. This tool reads every xmlns and xmlns:prefix declaration on the root element and makes them available, binding the default namespace to ns; the badge above the query box lists what is bound. Prefixes declared deeper in the document are not automatically visible, which is a limitation of resolving from the root; local-name() works around it.
