Log Analysis FAQ

We prioritize zero-trust security architecture. The entire application operates strictly within your browser's DOM. Logs uploaded or pasted are processed locally by JavaScript. Absolutely no data is transmitted over the network, ensuring complete air-gapped security for sensitive production data.

Our complex Regex mapping logic automatically structures raw text from standard Nginx (access/error), Apache, Node.js, Spring Boot, and Docker containers. It targets universal markers for severities like ERROR, FATAL, WARN, INFO, NOTICE, and DEBUG, as well as common ISO/UTC timestamps.

While ELK/Splunk excel at long-term storage and aggregation, Layerbit provides instant, lightweight forensic analysis for immediate IR needs, with zero setup. It renders every line as a DOM row with no virtualization, so it's built for the single log dump you'd actually paste during an incident — comfortably tens of thousands of lines — not a multi-gigabyte archive; split a file that large first (e.g. grep the relevant window) and load that slice instead.

The problem with reading logs linearly

A log file is a chronological record, which is the worst possible ordering for diagnosis. The line that explains an outage is usually one ERROR buried in ten thousand INFO lines, and the useful signal is often not the loudest error but the quiet warning that started forty seconds earlier.

Highlighting by severity changes the reading strategy from sequential to visual: errors and warnings become landmarks you can navigate between, and the density of them over time becomes a shape you can see. That is usually enough to find the window worth reading carefully, which is the actual goal.

First error, not worst error

Cascading failures produce dramatic downstream errors — connection pool exhausted, circuit breaker open, timeouts everywhere. The first anomaly in the sequence is usually the cause; everything after it is consequence. Work forward from the earliest deviation, not backward from the loudest.

Repetition is information

The same warning appearing a thousand times in ten seconds is a different problem from it appearing once an hour, even though the message is identical. Rate matters at least as much as content, and is invisible when you read one line at a time.

Timestamps and timezones

Correlating logs across services means their clocks and timezones must agree. Mixed local times, or one service in UTC and another not, will make a cause appear to follow its own effect. Log in UTC with an explicit offset.

A practical triage sequence

When handed a log file and a vague complaint, this order tends to find the answer fastest:

  • Establish the window. Find the first and last occurrence of the problem and ignore everything outside it. Most of the file is irrelevant.
  • Read the earliest error, not the most recent. The last error is usually the furthest from the cause.
  • Look immediately before it. Warnings and state changes in the seconds preceding the first error are where the explanation normally lives.
  • Check what stopped. The absence of an expected line — a heartbeat, a successful completion, a periodic job — is as diagnostic as the presence of an error, and much easier to miss.
  • Compare with a good run. Diffing a failing sequence against a working one isolates the divergence point quickly.

Logs are sensitive by default

Log files are among the most sensitive artefacts a system produces, and it is worth being conscious of that before pasting one anywhere. In practice they routinely contain bearer tokens in Authorization headers, session identifiers, full request URLs with query parameters, email addresses, internal hostnames and IP addresses, stack traces revealing file paths and library versions, and occasionally a password that ended up in a logged request body.

Which is precisely why this analyzer runs entirely in the page. Your log content is parsed and highlighted by local JavaScript and never transmitted — you can confirm that in your browser's Network tab, or work with the network disconnected entirely. Pasting a production log into a server-side analysis service is, functionally, a data disclosure.
