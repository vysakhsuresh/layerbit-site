 Database Engineering Standard

      
Layerbit's SQL Formatter is an essential utility for Database Administrators and Backend Engineers. It takes minified, poorly structured, or deeply nested queries and converts them into readable, standardized architecture.

      
      
    
        
  •  Syntax Colorization: Intelligent visual parsing separates commands, strings, and parameters.

 Advanced Formatting Controls

      
Go beyond basic indentation. Layerbit provides granular control over how your SQL statements are structured for code reviews and version control.

      
    
        
  •  Tabular Indentation: Align commas to the left or right of column names. This makes massive SELECT statements significantly easier to read and modify.
    • 
        
  •  Query Minification: Click the "Minify" button to compress sprawling SQL files into a single string. This is perfect for embedding raw SQL inside JSON payloads, application code, or YAML configuration files.
    • 
        
  •  Function Casing: Automatically force standard SQL functions (like COUNT(), MAX(), COALESCE()) to uppercase while preserving your table and column casing.
    • 
        
  •  Style profiles: Save a set of options (keyword, data type and identifier case, where AND/OR break, line width, dense operators, semicolon on its own line) under a name, switch between profiles, and export them as JSON so a whole team formats the same way.
    • 
        
  •  Checks with fixes: Six checks run as you type: SELECT * (expanded to the column list when you paste the CREATE TABLE), UPDATE/DELETE without WHERE, NOT IN over a subquery that can return NULL, comma joins, unused DECLARE variables and LIKE '%…'. Five have a one-click fix; Fix all applies them one at a time.
    • 
        
  •  Selection and many files: Format just the selected statement and leave the rest of the script alone, or choose many .sql files and download them formatted as one zip with a CSV report of syntax errors and checks per file.
    • 
        
  •  Autocomplete: Paste your CREATE TABLE statements and the editor suggests table names after FROM and JOIN, and column names after an alias and a dot. No database connection is needed.
    • 
        
  •  Persistent State: Your dialect choice, formatting preferences, and active query are saved to local storage. You will never lose your work if you accidentally refresh the browser.
    •

 Why query formatting is a review problem, not a cosmetic one

      
A query written as one 600-character line is not just unpleasant to read — it is effectively unreviewable. Every change to it produces a diff showing one line removed and one line added, so a reviewer cannot see whether you altered a join condition or only a column alias. Consistent formatting turns SQL into something version control can describe meaningfully.

      
That is the real argument for a formatter: not beauty, but making the WHERE clause you changed visible as a changed line rather than buried inside an unchanged wall of text.


      

        

          
 Keyword casing

          
Upper-casing reserved words (SELECT, JOIN, WHERE) separates language from identifiers at a glance. SQL keywords are case-insensitive, so this is purely for readability — but it is the convention nearly every style guide lands on.

        

        

          
 Clause alignment

          
Putting each major clause on its own line, with joins and conditions indented beneath, makes the query's shape match its logic. Nested subqueries become visibly nested instead of implied by parentheses alone.

        

        

          
 One column per line

          
For long select lists this is the difference between a reviewable diff and an unreviewable one. Adding a column becomes a single added line, which is exactly what you want a code review to show.

        

      


      
 Where dialects genuinely diverge

      
"Standard SQL" is closer to an aspiration than a description. Formatting has to know which dialect it is looking at, because the same characters mean different things:

      
    
        
  • Identifier quoting. ANSI and PostgreSQL use double quotes ("order"), MySQL uses backticks (`order`), SQL Server uses brackets ([order]). In MySQL, double-quoted text is a string literal unless ANSI_QUOTES is enabled — so the same query can parse differently depending on a server setting.
    • 
        
  • String concatenation. || in PostgreSQL and Oracle, CONCAT() in MySQL, + in SQL Server.
    • 
        
  • Row limiting. LIMIT n in PostgreSQL and MySQL, TOP n in SQL Server, FETCH FIRST n ROWS ONLY in Db2 and standard SQL.
    • 
        
  • Comment syntax. -- and /* */ are near-universal, but MySQL requires whitespace after --, so --comment is a subtraction of a negative rather than a comment.
    • 
        
  • Parameter placeholders. $1, ? and @name are all conventions you will meet, and a formatter must leave them intact.
    • 
      


      
 Formatting is not sanitising

      
Worth stating plainly: making a query readable does nothing about SQL injection. If any part of a query is assembled from user input by string concatenation, it is injectable whether it is beautifully indented or not. The fix is parameterised queries — placeholders bound by the driver, so user input is never parsed as SQL. A formatter is a readability tool, and reading a query is often how you notice a concatenation that should have been a parameter.

      
Equally, a formatter does not change how a query performs. It rewrites whitespace, never semantics: no clause is reordered, no join is rewritten, no index is chosen differently. For performance work you want EXPLAIN, not a formatter — though a readable plan is considerably easier to reason about alongside a readable query.


      
 Your queries do not leave the page

      
Production SQL tends to contain table names, column names, business logic and sometimes literal customer data in a WHERE clause. All of that is competitively and legally sensitive, and none of it should be pasted into a service you cannot inspect. This formatter is client-side JavaScript: the parsing and re-rendering happen in the page you have open, nothing is transmitted, and you can verify that in your browser's Network tab or simply by working offline.
