    WebRTC Architecture

    The link this page generates opens the LayerLink viewer on the other person's device; that page documents what a session ID actually grants, how quality adapts to the connection, and what to check when a session will not start.

    LayerLink utilizes WebRTC (Web Real-Time Communication) to establish a secure, peer-to-peer (P2P) connection directly between your browser and the viewer's browser. Once the initial handshake is completed, video data flows directly between the two devices without passing through a centralized server.

    Engineering FAQ

    The core JavaScript API required to capture a screen stream (navigator.mediaDevices.getDisplayMedia) is intentionally restricted by Apple and Google on mobile operating systems for security reasons. While a mobile device can view the stream, only a desktop/laptop environment can host it.

    Firebase Realtime Database acts purely as the "Signaling Server." In order for a P2P connection to occur, both browsers need to exchange connection data (SDP offers and ICE candidates) so they know how to find each other on the internet. Once the connection is established, Firebase's job is done. Chat, files and drawings never go through it.

    With a password, the connection details your browser and each viewer's browser exchange through the signalling service (the session descriptions and network candidates, which include IP addresses) are encrypted with AES-GCM under a key derived from the password with PBKDF2 (150,000 rounds of SHA-256). Someone who has the link but not the password cannot connect, and the signalling service only ever stores ciphertext for those fields. The password itself is never sent anywhere; send it to your viewers separately from the link.

    How a peer-to-peer connection is actually established

    Two browsers cannot simply find each other. Both are typically behind NAT with no publicly reachable address, so WebRTC solves this in stages — and understanding them explains both the privacy properties and the occasional failure:

    • Capture. getDisplayMedia() asks the operating system for a screen, window or tab. The browser, not the page, renders that permission prompt.
    • Signalling. The two peers must exchange session descriptions (SDP) and candidate network addresses (ICE). This needs a third party, because at this point they have no way to reach each other. LayerLink uses a signalling service for exactly this handshake — it carries connection metadata and never any video.
    • Connection. With candidates exchanged, the peers attempt a direct path. STUN servers help each side discover its own public address; if a direct route is impossible, a relay is required.
    • Media. The stream flows directly between the browsers, encrypted with DTLS-SRTP, which is mandatory in WebRTC rather than optional.

    Sharing needs a desktop

    Screen capture is deliberately unavailable to web pages on iOS and unreliable on Android — the operating systems do not expose it. So hosting a session requires a desktop browser. Viewing one works on any modern device, since receiving a video stream needs no special permission.

    A few viewers, all direct

    Every viewer has a separate peer connection to your browser, so your upload is shared between them. That suits a handful of people; serving many viewers needs an SFU, a media server that receives the stream and redistributes it, which means your video passes through infrastructure rather than going peer to peer.

    When direct fails

    Symmetric NAT and restrictive corporate firewalls can block every direct path. Without a TURN relay the connection simply does not establish. If a session fails on a corporate network but works on a home one, this is almost always why.

    What a browser cannot do

    Desktop remote-support programs install software on both computers. A web page cannot, so some things those programs do are not possible here, and LayerLink does not pretend otherwise:

    • Remote control. A viewer cannot move your mouse or type on your computer. Browsers give pages no way to inject input into other applications.
    • Unattended access. Someone has to be at the sharing computer to start the share and pick a screen, every time.
    • Restarting the remote computer and reconnecting afterwards.
    • Printing to a printer attached to the other computer.
    • Wake-on-LAN, or reaching a computer that is asleep or switched off.
    • Sharing from a phone. iOS and Android do not let web pages capture the screen; phones can view, chat, draw and send files.

    What does work in a browser, and is built in: several viewers, a room password, approving each viewer, audio from a tab or the system plus your microphone, text chat, file transfer in both directions, drawing over the shared picture, and recording to a file on your own computer.

    What to know before you share a screen

    Screen sharing leaks more than people intend, and the mistakes are consistent enough to be worth listing:

    • Share a window, not the whole screen, whenever the task allows. Full-desktop sharing exposes every notification that arrives — including message previews and password-reset emails.
    • Notifications. Enable do-not-disturb first. A toast notification appearing mid-demo is the single most common accidental disclosure.
    • Browser tabs and bookmarks. Sharing a browser window reveals your other tab titles and your bookmarks bar, which are often more revealing than the page you meant to show.
    • Credentials on screen. A terminal with an exported token in its scrollback, or an IDE with a .env file open in another tab, is visible the moment you switch to it.
    • Ending the session. Stop the share explicitly rather than closing the tab and assuming. The browser shows an active-share indicator; confirm it has gone.

    The honest privacy position

    LayerLink is the one tool on this site that is not purely local, and it is badged Cloud API for that reason. What we can say precisely: the video stream, chat, files and drawings travel directly between the browsers and are encrypted in transit; the signalling service sees only the connection metadata required to introduce the peers, never media, and with a room password even that metadata is stored encrypted. The service does see each viewer's chosen display name, the room settings, and when people join. What we do not claim is that this is equivalent to the fully offline guarantee the other tools make — it is a different and weaker property, and the badge exists so you know which you are getting before you click.
