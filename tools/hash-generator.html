What a hash is for, and what it is not for

A cryptographic hash turns input of any size into a fixed-size digest — 256 bits for SHA-256 — such that the same input always gives the same digest, a one-bit change anywhere gives a completely different one, and finding two inputs with the same digest is computationally infeasible. That last property is what separates a cryptographic hash from a checksum like CRC32, and it is the one MD5 and SHA-1 have lost.

Verifying a download

A release page publishes sha256sum values so you can confirm the file you received is the file they built. Drop the file here, paste the published digest into the verifier, and the comparison is done in the page. If the digests differ the file is corrupt or altered; if they match, you have the file the publisher hashed — which only proves anything if you trust the page you copied the digest from.

Webhook signatures

Stripe, GitHub, Slack and most payment providers sign each webhook with an HMAC over the raw body using your shared secret. Paste the exact body and the secret and compare the HMAC-SHA256 here with the header they sent. The most common failure is hashing a re-serialised body rather than the raw bytes — a single reordered key or trailing newline changes everything.

Content addressing and deduplication

Git names every object by its SHA-1 (moving to SHA-256), and object stores, package managers and build caches use a digest as the key. Hashing here lets you confirm what key a blob would receive, or check whether two files that look identical actually are.

Not for passwords

None of these functions is suitable for storing passwords. They are fast by design, and a GPU computes billions of SHA-256 values per second, so a leaked table of plain hashes falls to a dictionary attack in hours. Password storage needs a deliberately slow, salted, memory-hard function: Argon2id, scrypt or bcrypt. This page will not offer one, because doing it in a browser page would suggest it is fine to do it there.

HMAC: a hash with a key

An HMAC (RFC 2104) is a hash computed in a specific way over a secret key and a message. Anyone can compute a plain SHA-256 of a message, so a plain hash proves nothing about who sent it; an HMAC can only be produced by someone who holds the key, which turns it into an authentication tag. The construction — hash the key XOR an inner pad concatenated with the message, then hash the key XOR an outer pad concatenated with that — exists because naively hashing key + message is vulnerable to a length-extension attack on every Merkle–Damgård hash, SHA-256 included. Use the construction, never the naive concatenation.

When a key is entered above, every row switches from a plain digest to an HMAC with that key. The key is handled as UTF-8 text. If your integration hands you a key as hex or base64, decode it first; a key of the string "a1b2c3" and a key of the bytes 0xa1 0xb2 0xc3 produce different tags, and that mismatch is the second most common webhook signature bug.

MD5 is not provided by the Web Crypto API at all — browsers dropped it deliberately — so the value shown here comes from a small implementation of RFC 1321 included in the page and checked against the RFC's own test vectors. It is here because you will still meet MD5 in the wild: old download pages, Amazon S3 ETags for single-part uploads, database migration checksums, and UUID v3. Being able to check one is not the same as being allowed to choose one.

How the page computes them

The SHA family is computed by crypto.subtle.digest(), and HMACs by crypto.subtle.sign() with an imported HMAC key. Both are native browser code, which is why a 200 MB file hashes in a few seconds. A file is read into memory in full before hashing, because the Web Crypto API has no streaming digest; that puts a practical ceiling around a gigabyte depending on the device. The verifier compares digests with a fixed-time loop over the full length rather than a string equality, and treats case and surrounding whitespace as irrelevant so a checksum copied from a web page with a stray newline still matches.

No. A hash is one-way: the digest is a fixed 256 bits regardless of input size, so infinitely many inputs map to each digest and there is no inverse function. What attackers do instead is guess: precompute digests of likely inputs (a dictionary, or every string up to eight characters) and look yours up. A hash has no key: anyone can compute it, so it proves integrity against accidental change but not against a deliberate one, since an attacker who alters the message can recompute the hash too. An HMAC mixes a secret key into the computation using the RFC 2104 construction, so only a holder of the key can produce a valid tag. Use a hash to detect corruption; use an HMAC to authenticate a message from a party you share a secret with.
