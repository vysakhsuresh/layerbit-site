When a script is the right answer — and when it is not

A script is the most cost-effective software there is, right up to the point where it becomes the most expensive. The distinction is usually about who runs it and how often, so it is worth being deliberate rather than letting a one-off grow into infrastructure by accident.

  • A script is ideal for a task run by one technical person, whose failure is immediately visible to that person, and where being wrong costs a rerun rather than a recovery.
  • A script is a liability once it runs unattended on a schedule, other people depend on its output, its failure is silent, or the person who wrote it has moved on. At that point it needs the things real software has — logging, alerting, tests, documented recovery — and pretending otherwise just defers the cost.

We write both, and we will tell you which one you are buying. A throwaway is a legitimate deliverable; a throwaway that has quietly become load-bearing is a problem worth naming early.

Idempotent and resumable

Any script that mutates data should be safe to run twice and able to resume after an interruption. Processing 100,000 records that dies at 60,000 should not mean starting again — or worse, double-processing the first 60,000.

Dry-run first

Anything destructive gets a mode that reports exactly what it would do and changes nothing. The cost is an afternoon; the return is the first time someone runs it against the wrong environment and nothing happens.

Logs that survive

Output to a durable location with timestamps, not just the terminal. A scheduled script whose output went to a closed SSH session is a script you cannot debug and cannot prove ran.

No secrets in source

Credentials come from the environment or a secrets manager, never from a literal in the file — because scripts get copied, pasted into tickets and committed to repositories far more casually than applications do.

Fail loudly

Shell scripts should start with set -euo pipefail. Without it, a failed command mid-pipeline is ignored and the script reports success — which is how a backup that has silently written zero bytes for six months happens.

One at a time

A scheduled script that sometimes runs longer than its interval will eventually overlap with itself. A non-blocking lock — flock -n or a lease with a TTL — makes the second run skip rather than compete.

Typical work

The requests that come up most often: extracting and reshaping data between systems that have no integration; parsing and summarising log files to answer a specific recurring question; bulk operations against an API with correct rate limiting and resumability; scheduled report generation and delivery; database maintenance and cleanup with verifiable safety; and one-off migrations where correctness matters far more than elegance.

Deliverables are the script itself, written to be read by whoever inherits it, a short README covering how to run it and how to recover when it fails, and the scheduling configuration if it is to run unattended.
